# interview-notes.md — Engineering Decisions Worth Explaining
This is the only document in the set written for discussion/demo purposes rather than as an engineering contract. It exists specifically because interview-oriented language ("this is the payoff," talking-point framing) was found embedded inside `system-spec.md`/`architecture.md` during the adversarial review and was removed from those documents for credibility as engineering artifacts (FINAL-AUDIT.md #16) — it belongs here instead.

## The Durable Job Queue
"I built async processing on Postgres alone using `SELECT ... FOR UPDATE SKIP LOCKED` rather than reaching for a message broker. This gives exactly-once **claiming** — a job is never picked up by two workers at once — but I can explain clearly why it isn't exactly-once **processing**: if an instance crashes between a successful external API call and the database commit that records it, the job gets retried and the external call happens again. I made that tradeoff explicit instead of overclaiming, and bounded its cost by writing to the cache before committing, so a retry after a crash usually hits cache instead of calling the AI provider a second time."

## The WebSocket Reversal
"I originally designed WebSocket push for job status, then reversed that decision once I worked through what actually happens with two backend instances on a platform with no shared session affinity — a client's WebSocket connection could land on an instance that never learns the job finished. Short-polling was the correct tradeoff once I traced that through, not just the easier one. I'd rather describe a decision I reversed for a good reason than one I never examined."

## The Refresh-Token Concurrency Bug
"During review I found a real bug in my own auth design: two API calls hitting a `401` at nearly the same moment would both try to refresh the token, and my reuse-detection logic would treat the second one as a stolen-token replay and log the user out. I fixed it two ways — a single-flight refresh pattern on the frontend so only one refresh call is ever in flight per tab, and a short grace window on the backend for the case a frontend fix alone can't cover, like two separate browser tabs. I think walking through how I found and fixed that is a stronger interview story than never having had the bug."

## Redis Fail-Open vs Fail-Closed
"Caching and rate-limiting both depend on Redis, but I made them fail differently on purpose. If Redis goes down, the cache fails open — worst case, a request runs slightly slower and calls the AI provider directly. But rate-limiting and per-user AI quotas fail closed — if I can't verify the quota, I reject the request, because the alternative is unlimited calls against a metered API with a real dollar cost. Same dependency, different failure mode, because the cost of being wrong is different in each direction."

## Treating AI Output as Untrusted Input
"Every LLM and Whisper response is schema-validated before it's ever stored or shown to a user, and rendered through Angular's default auto-escaping rather than raw HTML. I also frame the job description and resume text explicitly as untrusted data in the prompt, not instructions, as a real (if not perfect) mitigation against prompt injection. Because AI output only ever produces display text and never triggers a further privileged action in my system, the worst case of a successful injection is a bad Gap Analyzer result, not a security breach — I can explain why that containment matters as much as the input-side mitigation."

## Two Cleanup Sweeps, Not One
"My first version of file cleanup only handled objects that were uploaded to storage but never got a database row — a partial-failure case. During review I realized that doesn't catch the much more common case: a user replacing their resume, where the old file's database row never goes away, it's just marked inactive. I added a second, purpose-built sweep for that case instead of assuming one mechanism covered both. It's a good example of a bug that's obvious once you trace an actual user flow end-to-end instead of reasoning about failure categories in the abstract."

## Honest Framing of Free-Tier Scale
"I can say clearly what this architecture is and isn't. It's correct under crashes, retries, concurrent requests, and multiple backend instances, and I can point to the specific tests that prove each of those properties. It is not a claim that this scales to thousands of concurrent users on a free-tier stack — the per-user AI quotas protect an individual user's cost exposure, but they don't protect an organization-level provider rate limit if many users are active in the same minute, and I say that explicitly rather than papering over it. Knowing the difference between 'correct at this scale' and 'production-ready at any scale' is itself the point I want to make."
